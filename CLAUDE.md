# CLAUDE.md

Guidance for Claude (and other agents) working in this repository.

## What this is

**RTLify for Claude** — an open-source Chrome/Chromium extension
(**Manifest V3, vanilla JS, no build step, no dependencies**) that makes
right-to-left text display correctly in the Claude AI web app (`claude.ai`,
`claude.site`): responses, user messages, and the input box. It detects the
**Arabic script**, so it covers Arabic, Persian/Farsi, Urdu, Pashto, and other
Arabic-script languages.

It is a trust-focused alternative to closed-source RTL extensions: everything
runs locally, the only permission is `storage`, and it makes **no network
requests**. Keep it that way.

## Hard rules

- **Scope: RTL display in Claude.** The extension detects Arabic-script text and
  displays it right-to-left, only inside conversation content and the input box.
  Keep new work consistent with that purpose.
- **No network, no tracking, no extra permissions.** `storage` is the only
  permission. Don't add `host_permissions`, analytics, remote fetches, or new
  permissions without a very good reason.
- **No dependencies / no build step.** Plain HTML/CSS/JS loaded directly by the
  browser. Don't introduce bundlers, frameworks, or npm runtime deps. (Node is
  used only for the dev-time test runner; Python only for icon/zip scripts.)
- **License is MIT.** Don't reintroduce other licenses.
- **Independent implementation.** Don't copy code or names from other
  extensions; this is original.

## Architecture (where things live)

```
manifest.json   MV3 config. content_scripts.js order matters:
                ["src/constants.js","src/detect.js","src/content.js"]
src/
  constants.js  self.RTL_CONFIG = { storageArea:"sync", defaults:{enabled,inputBoxEnabled,uiLang} }
                Loaded first in ALL three contexts (content/popup/worker) =
                single source of truth for settings.
  detect.js     self.RTL_DETECT = { detectDir }. detectDir(text) -> "rtl" | null
                ("rtl" when the text contains any Arabic-script char). Also
                CommonJS-exported so test/ can require it. UNIT-TESTED.
  strings.js    self.RTL_STRINGS = { ar, en } popup i18n table. Same dual
                browser/CommonJS export as detect.js (the test requires it).
  content.js    The core. Scans message content, applies dir="rtl". See below.
  content.css   Alignment + isolates code/KaTeX as LTR inside RTL blocks.
  background.js  Service worker; seeds defaults on install. Uses
                importScripts("constants.js") (path is worker-relative → src/).
  popup.*       Toolbar popup: 2 toggles, interface language (ar/en), and
                GitHub + Buy-Me-a-Coffee links.
icons/          PNGs generated by scripts/make_icons.py (pure Python, no deps).
scripts/build_zip.py  Packages the Web Store ZIP (pure Python, no deps).
test/           node:test suite (detection + manifest validation).
.github/workflows/ci.yml  runs `npm run check` + `npm test` on push/PR.
```

### How content.js works (the important part)

- Reads settings via `RTL_CONFIG`; detection via `RTL_DETECT.detectDir`.
- **Scoping is everything.** It only flips elements inside Claude's message
  containers, so the sidebar / chrome are never touched:
  - `RESPONSE_ROOTS` = `.font-claude-message, .font-claude-response-body, .standard-markdown`
  - `USER_MESSAGE`  = `.whitespace-pre-wrap.break-words`
  - `MESSAGE_SCOPE` = the two above; `applyContentDir()` bails unless the
    element is `closest(MESSAGE_SCOPE)`.
  - These selectors are the ONE Claude-specific dependency and the first place
    to look if RTL stops working after a Claude UI update.
- Direction policy: contains Arabic-script → `rtl` (whole element), else leave
  alone. This is deliberately NOT a majority vote — an Arabic sentence full of
  English terms must still read RTL. Inline Latin/code stays LTR via the
  browser's bidi algorithm + content.css.
- `dir` is set with the `dir` attribute; processed elements are marked with
  `data-rtl-dir` (content) / `data-rtl-input` (composer) so we skip redundant
  writes and can `revert()` cleanly on disable.
- A `MutationObserver` (`{childList, subtree, characterData}`, **not**
  `attributes` — that's what prevents an infinite loop) feeds a
  `requestAnimationFrame`-batched flush. Work is split: `pendingTrees`
  (childList) → full subtree scan; `pendingBlocks` (characterData/streaming) →
  re-check just that block.
- `SKIP_SELECTOR` (pre/code/katex/contenteditable/textarea/input) is never
  flipped; the composer/edit box are handled separately by `applyEditorDir`,
  gated on `inputBoxEnabled`.

## Conventions / gotchas

- `RTL_CONFIG` / `RTL_DETECT` / `RTL_STRINGS` are globals shared via
  `self.X = ...`. They work because all files in one `content_scripts` entry
  share an isolated world, the popup loads `constants.js`/`strings.js` before
  `popup.js`, and the worker `importScripts` them. If you add a new context,
  load the shared files first.
- `importScripts("constants.js")` in `background.js` is **worker-relative**
  (resolves to `src/constants.js`). Do NOT change it to `"src/constants.js"`.
- Keep `manifest.json` `description` ≤ 132 chars (a test enforces this).
- If you change settings keys/defaults, edit them **only** in `constants.js`.
- **Chrome Web Store listing text has two sources.** The store **title** and
  short summary come from `manifest.json` (`name` / `description`) — the title
  is NOT editable in the dashboard, so changing it means editing `name`, bumping
  `version`, `npm run build`, and re-uploading the ZIP. The **long store
  description** is dashboard-only (the store does not pull from GitHub); its
  source-of-record copy lives in `store-assets/store-listing.md`, with SEO /
  ratings / traffic guidance in `store-assets/growth-notes.md`.

## Developing & testing

No install needed (Node ≥ 18 for the built-in test runner):

```bash
npm run check   # node --check on all JS
npm test        # unit + manifest tests
npm run ci      # both (mirrors GitHub Actions)
npm run icons   # regenerate icons after a design change
npm run build   # package dist/rtlify-for-claude-v<version>.zip for the Web Store
```

No build/transpile step exists or should be added — `npm run build` only zips the
runtime files. Bump `manifest.json` `version` before each store release, and
bump `package.json` `version` to match (the build reads the version from
`manifest.json`, but keep the two in sync as hygiene).

Load it in the browser: `chrome://extensions` → Developer mode → **Load
unpacked** → select the repo root → **Reload** ↻ after edits.

When you add behavior, add or update a test under `test/` so CI guards it.
